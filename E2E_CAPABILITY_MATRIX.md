**Scope:** Handyman-Backend only; contracts for Customer Care Frontend, Operations/Manager `/admin`, field PWA, and native Android are derived from this repository without entering consumer repositories.
**Companion:** gap details and acceptance criteria are in `FINAL_BACKEND_GAP_AUDIT.md`.

## 1. How to read this matrix

- **IMPLEMENTED** means the Backend route/service/table authority exists and no open implementation gap was identified for that capability. It does **not** mean its consumer UI or production environment has passed live E2E.
- **PARTIAL** means real implementation exists but a named gap prevents a complete readiness claim.
- **CONFIGURATION** means the code capability exists but data, provider, environment, or operational evidence is absent.
- **FRONTEND-DEPENDENCY** identifies client-owned presentation/integration work; it is not used to call an existing Backend API missing.
- “Source/static” means current source and OpenAPI were traced but that exact journey was not freshly executed in this audit. Historical certification is supporting evidence, not a new PASS claim.
- Every implemented consumer journey remains subject to integrated staging gate **BA-08** unless a fresh local result is explicitly listed.

## 3. Consumer-specific contract boundaries

### 3.1 Customer Care Frontend

- Use `/api/v1` domain APIs; do not expect the Backend to mirror a frontend `/admin` or page route hierarchy.
- Support both staff bearer sessions and the signed Care workspace credential where applicable. A workspace credential is not a User session and cannot be substituted for one.
- Treat `handymanRequestId`, `executionScopeId`, quotation/version, payment, invoice, warranty, claim, and evidence IDs as opaque; persist idempotency keys for safe retries.
- Use customer-safe quotation/material projections. Internal price snapshots, crew assignment internals, provider/BM entitlement facts, and Finance-only commands are not Care-authoritative data.
- Payment proof upload is a fact for Finance review, not a payment confirmation or PAID transition.
- Report integration failures with exact path and `error.code`; no consumer repository result was available to this audit.

### 3.2 Operations/Manager `/admin`

- Operations and Manager are separate permission profiles. `tenant_company.manage` alone does not grant Finance, settlement, or CLOSE.
- Catalog, QR/geofence, scheduling, assignment, dispatch, QC, and commercial APIs already exist. Admin screens are client work; approved API tooling is a valid alternative for BA-18.
- Manager CLOSE requires the dual permission guard and all readiness conditions. A frontend “Manager” label is not sufficient; production role grants must match the Backend permission resolution.
- Finance proof verification, ledger correction, reconciliation, and settlement are distinct commands with distinct permissions. Do not combine them into one client-side “mark paid/settled/closed” action.

### 3.3 Field PWA and native Android

- Both consume the same assignment, arrival, work-session, material, evidence, variation, QC, and BAST contracts. Native Android does not need a second business authority.
- Send the same raw QR string and `deviceLocation`; never calculate the authoritative geofence result locally or reuse a superseded challenge.
- Work starts only through the server work-session command after all prerequisites; QR `VERIFIED` alone is not start work.
- Browser push uses service-worker subscriptions and endpoint rotation/revocation. Android uses FCM token registration/rotation/revocation. Neither calls a push-send route.
- After BA-01, Android must treat `pushToken` as write-only and must not depend on seeing it in registration/list/deactivation responses.

### 3.4 Tenant PIC and external authorities

- Quotation decision and BAST acceptance are separate personal actions. An unexpired ISSUED quotation and active PIC binding are mandatory for the former; BAST evidence/acceptance rules govern the latter.
- Payment providers/banks, Finance, and external payout rails do not become Backend client authorities. Finance verification and internal settlement records remain distinct.
- External e-signature is not implied by `signatureDigest`; BA-22 requires an explicit Legal/Security/Product decision before any provider integration is claimed.

## 4. Coverage conclusion

The approved Backend scope has **no newly proven missing lifecycle engine**. The dominant implementation is present end to end, with three reproduced code/migration defects and named evidence debt. Production readiness cannot be inferred from that breadth: **BA-01 through BA-11 remain release blockers**, and live consumer/environment evidence is still absent.
