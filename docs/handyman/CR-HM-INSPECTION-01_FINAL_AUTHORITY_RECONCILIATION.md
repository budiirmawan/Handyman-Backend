## 2. Exact minimal schema and authority changes required

No migration or runtime change is authorized by this review. If the amendment is ratified, the minimum additive changes are:

1. **Request assignment history:** append-only request/client/building-scoped assignment records using authenticated `users.id` as the Field identity. Persist assigner, server time, predecessor link, and mandatory reassignment reason. Derive the current assignment from the chain or enforce one-current-assignment under a request lock/unique constraint. No provider, crew, Execution Scope, tenant/PIC, or BM identity.
2. **Versioned technical report:** immutable report versions linked to request, 0381 inspection and assignment; unique `(request_id, version_number)`; submitter and server time; bounded findings/diagnosis/recommended F9 scope. Add optional labor/material estimate-quantity lines with existing units only. No prices, amounts, currency or evidence references.
3. **Review decisions:** one immutable `ACCEPTED`/`RETURNED` decision per version, reviewer and server time; return reason required. Reviewer must differ from that report version's submitter. Only one version may be accepted per request; corrections append a version after `RETURNED`.
4. **Diagnosis source:** add nullable `source_inspection_report_id` to 0382 through a **new** additive migration, not by editing migration 0382. For `INSPECTION_REQUIRED`, the diagnosis service resolves the accepted report server-side, checks its immutable `ACCEPTED` review and stores that version id. Existing/direct-diagnosis rows remain null and are never backfilled. This supersedes the earlier proposal to materialize diagnosis during report acceptance or link diagnosis from the review row: keep the existing separate diagnosis write after acceptance, put the accepted report id directly on 0382, and preserve the current authenticated diagnosis writer/server timestamp unless separately amended.
5. **`NOT_INSPECTABLE` resolution:** persist Operations' action, reason, actor and time as separate append-only business state. Do not use an operational event as the decision record or infer `REFERRED` without a diagnosis. `NOT_INSPECTABLE` must fail the quotation DRAFT prerequisite even if other data exists. If reschedule means another physical visit after the 0381 row exists, approve the F2 amendment and attempt history first. Cancellation and escalation need explicit terminal disposition/target semantics.
6. **RBAC and routes:** register `handyman.operations.inspection.assign`, `handyman.field.inspection.report.submit`, and `handyman.operations.inspection.report.review` in the existing permission registry and unassigned-by-default set. No new role or auto-grant. Preserve existing paths/GETs; in-scope POST inspection requires assigned Field authority; inspected-path POST diagnosis requires accepted report and binds its id; direct `DIAGNOSIS` remains unchanged. Put bounded assignment/report/review routes in a separate module and amend the API inventory explicitly.
7. **Quotation DRAFT gate:** require the accepted report and matching 0382 source reference before initial DRAFT creation and every later DRAFT revision when persisted triage is `INSPECTION_REQUIRED`. Do not add an issue gate or change PIC approval, session/binding, Execution Scope, or CR-HM-04 assignment.

## 3. Compatibility, concurrency, audit and idempotency

- **History/API:** preserve 0381/0382 and quotation history; nullable source-report references remain null for legacy/direct diagnoses. Keep historical read routes. New writes cannot use the old `tenant_company.manage` path to bypass assignment/review. Existing quote versions are not retroactively invalidated. A new DRAFT from a pre-cutover `INSPECTION_REQUIRED` request with no accepted report remains subject to the cutover decision; grandfathering requires a durable explicit rule.
- **Concurrency:** serialize assignment/reassignment, physical capture, report-version allocation, review, diagnosis-link write and DRAFT gate on the request/report aggregate. Retain unique constraints for current assignment, `(request_id, version_number)`, one review per version, one accepted version per request and the existing one-diagnosis-per-request rule. No acceptance may race a later report version. A quotation revision must load the request's persisted triage/report/diagnosis chain before inserting a DRAFT.
- **Idempotency:** use CR-BE-IDEMPOTENCY-CORE-01 `executeIdempotent()` / `request_idempotency_records` for assignment/reassignment, report submission/review and any new physical-capture adapter. Use server operation keys and normalized `Idempotency-Key`; fingerprint resource IDs and normalized body; identical replay returns the original compact success, changed body conflicts, and rows/events/idempotency completion share one transaction. Respect the existing 65,536-byte response limit. No bespoke idempotency store.
- **Audit:** assignment/reassignment reason, report version and review decision are business rows. Append actor/resource/version/action events in the same transaction through the existing event seam; events are audit-only and omit raw keys/report payloads.
- **Firewalls:** no new RBAC/provisioning framework, auto-grants, SaaS tenant provisioning, evidence engine or commercial estimate authority. Handyman integration ownership, BM channel-level attestation, Tenant/PIC quotation authority, CR-HM-04 execution gate, S1 and B12 remain unchanged.

## 4. Owner decisions still needed before freeze

The business directions in proposals 1–8 are recorded; the remaining questions are how to resolve their interaction with frozen authorities:

1. **Second visit after `NOT_INSPECTABLE`:** does `reschedule` authorize another physical visit after the immutable 0381 row exists? If yes, ratify an F2 amendment and attempt-history model. If no, define how rescheduling works without another inspection. Confirm that actual schedule changes use CR-HM-05.
2. **Cancellation/escalation:** does cancellation use a separate terminal inspection resolution or require an F1 request-status amendment? What escalation destination/terminal state applies when there is no diagnosis? Existing CR-HM-03 `REFERRED` cannot be inferred from `NOT_INSPECTABLE` alone.
3. **Legacy cutover:** are pre-cutover `INSPECTION_REQUIRED` requests without a report blocked from new DRAFT preparation until the new accepted-report chain exists, or explicitly grandfathered? No synthetic assignment/acceptance; existing reads and quote versions remain.
4. **Reassignment timing:** confirm the suggested bounds (before physical capture or after a returned report; not while a report is pending or accepted) and whether a replacement assignee may submit the next correction. Reason and immutable history are mandatory under proposal 5.
5. **Diagnosis actor continuity:** confirm the compatibility default that the existing authenticated diagnosis writer records diagnosis after acceptance, with server time, while 0382 references the accepted report. If the Field author becomes the diagnosis actor/time, that is an additional F7/F2 amendment.
6. **Formal amendment ratification:** ratify the narrow F8 amendment proposal and attach its reference to the existing CR-HM-03 roadmap row without renumbering. Direct-quotation eligibility remains a separate pending authority and need not be decided here.

## 5. Freeze-readiness verdict

**NOT FREEZE-READY.** The owner direction is coherent as a proposed additive authority, and the requested baseline is verified. The current runtime cannot enforce it: assignment, report and review persistence/routes/permissions do not exist; 0382 has no accepted-report source reference; the legacy POST routes use the existing manage permission; and `NOT_INSPECTABLE` currently reaches ordinary diagnosis/quotation preparation without an outcome check. The proposed F8 amendment is not ratified, and the `NOT_INSPECTABLE` operations need F1/F2-compatible resolution semantics.

Do not mark CR-HM-INSPECTION-01 or the amendment FROZEN until §4 is resolved and the F8/roadmap amendment is ratified. The direct-quotation service-eligibility policy remains separate.
