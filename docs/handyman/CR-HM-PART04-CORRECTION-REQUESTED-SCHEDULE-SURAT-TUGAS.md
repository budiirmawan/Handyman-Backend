## Minimal correction

- Requested date = existing tenant/request preference; confirmed execution date = existing Operations-confirmed appointment; Surat Tugas = existing assigned Work Order/Mobile projection. None is silently substituted for another.
- An EXECUTION proposal can omit **both** existing `startAt/endAt` inputs. Backend resolves an existing coordinated tenant choice first, otherwise the request's active `preferredWindowStart/End`. Missing dates are never invented from creation time, inspection time or a new date field. Existing explicit-date clients remain compatible when matching the recorded/coordinated window; partial pairs, past/oversized windows and uncoordinated differences are denied.
- INSPECTION still supplies its own separate visit window and never borrows or overwrites the execution preference. Inspection remains optional.
- Preference creates a PROPOSED visit only: no automatic TENANT_SELECTED/CONFIRMED state, reservation, dispatch or execution. Existing stored exact tenant-choice provenance, state/version, live worker eligibility, Building/Client authorization, atomic capacity exclusion, audit rollback and idempotency remain mandatory at confirmation. Confirmation no longer requires a currently provisioned BM API/secret merely to consume an already-verified stored choice; the existing authenticated ingest remains protected and is not replaced by an Operations claim.
- Existing visit reads and field request/Work Order details append `schedulingReadiness` using the **existing bundle schema/service**. Original/revised dates remain in that history; confirmed dates remain in `visit.executionVisit` and the unchanged feed fields. Care's existing read projection now also includes the existing `supersedesReadinessId` link. These are read mappings, not additional date persistence.
- Detail execution visits must match the current scope/active crew, like the existing feed. Another crew's historical appointment is not returned as the current assignment's execution date; the underlying history is not deleted. Assignment IDs, crew/helper/Lead objects and existing Surat Tugas endpoints are not recreated.
- Changing a requested preference does not move a confirmed appointment. Existing cancellation/re-proposal/tenant-coordination and immutable appointment/history safeguards remain; no unilateral confirmed reschedule, new scheduling engine or new assignment workflow was introduced.
- BM verification is optional (`NOT_INTEGRATED`, explicitly **not** BM approval). Existing permit/access facts, exact unit/window, authorized scope/current assignment, eligible roster/current Lead, release, arrival/session/material and safe pause/replay guards remain. If an optional verifier is supplied, rejected/revoked/expired/mismatched/stale/unavailable results still fail closed; an outage cannot select manual mode. No request/body/environment override, BM approval producer, BM permit-management module or API transport was added.
- Finance/tax, approved commercial scope, QC, canonical BAST and Manager FINAL CLOSE authority were not changed.
