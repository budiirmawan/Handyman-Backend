# CR-HM-QC-AUTHORITY-01 — Handyman Operations PR #13 handoff

Backend branch `arena/c4e0d6f4-handyman-backend`, based on `37e62ca` (P0-A, **not** repeated). All paths below are relative to `API_PREFIX` (normally `/api/v1`). Authentication and an ACTIVE assignment to the exact Client **and Building** are required on scoped actions. HTTP success uses the existing `{ success, data }` envelope; failures use the existing error envelope. This handoff does not authorize an Operations persona to decide QC.

## Authority and sequence

1. **Before inspection** a Client QC configuration manager with an explicit `handyman.qc.configure` grant publishes a nonempty immutable checklist version:
   - `POST /handyman/clients/:clientId/qc-checklist-versions` with `{ "code": "HANDYMAN_FINAL", "versionNumber": 1, "requiredItemKeys": ["PHOTO", "FUNCTION"] }`. The keys are illustrative, not a seeded standard. Versions are numbered sequentially per Client/code; duplicates with identical keys replay; mutations and empty/duplicate keys are rejected. `GET` at the same path lists published versions. Provision/grant the permission explicitly; migrations do **not** assign it to an Operations role.
   - `POST /handyman/execution-scopes/:executionScopeId/qc-checklist` with `{ "templateVersionId": "<published version UUID>" }`; `GET` at the same path returns `{ checklist }` (possibly `null`). The binding response has `checklistIdentity` (e.g. `HANDYMAN_FINAL@v1`), `requiredItemKeys`, `templateVersionId`, `templateCode`, `templateVersionNumber`, `configuredAt` and `boundAt`. Do not send required keys in the binding or OPEN payload; the server pins the published version. A legacy pre-version manifest can **only** be bound explicitly between runs if its identity and keys match; binding never grants validity to its earlier run.
2. **Assigned Supervisor inspects.** The user must have `handyman.qc.manage`, the active/effective reporting line from the currently assigned Crew Lead, an active workforce profile in the same Client, and exact-Building access, and must **not** be the executor/crew member. A reporting line or broad Operations permission on its own does not suffice. `POST /handyman/execution-scopes/:executionScopeId/qc-runs` with `{ "checklistIdentity": "<value from binding>", "idempotencyKey": "<unique key>" }` opens a fresh run with all required items initialized to `NOT_CHECKED`. The response includes `data.run.id` and `data.run.version`; `GET` on that path lists runs, and `GET /handyman/qc-runs/:qcRunId` returns the run, items, bound evidence and append-only events. Reads additionally admit the assigned PIC or `tenant_company.read` staff inside the exact Building, but do not confer decision authority.
3. **QC evidence and item decisions.** The assigned PIC uploads genuine nonempty bytes with `purpose: "QC_EVIDENCE"` using `POST /handyman/field/execution-scopes/:executionScopeId/evidence/upload` (multipart field `file`, other fields per existing field-evidence contract). The upload must be `VERIFIED` and newer than the current run/prior failed decision. The Supervisor binds its server-issued `hm-ev://<upload UUID>` reference with `POST /handyman/qc-runs/:qcRunId/evidence` body `{ "evidenceReference": "hm-ev://...", "expectedVersion": 1, "idempotencyKey": "..." }`; use returned `data.runVersion` for the next write. `POST /handyman/qc-runs/:qcRunId/items` body `{ "itemKey": "PHOTO", "outcome": "PASS", "expectedVersion": 2, "idempotencyKey": "..." }` updates only a required key. Version on item set is optional but recommended; each successful item/evidence write increments run version. Neither metadata-only uploads nor altered/deleted storage bytes count as verified evidence.
4. **Supervisor explicitly FINISHes.** `POST /handyman/qc-runs/:qcRunId/finish` requires `{ "outcome": "PASSED" | "FAILED", "expectedVersion": <current run version>, "idempotencyKey": "..." }`. For `FAILED`, supply a nonblank `reason` (max 2000 chars). For `PASSED`, **omit** `reason`. The server independently guards a PASS: latest open run, pre-run version binding and every required item `PASS` (not `NA`), all Work Sessions completed/checked out, zero unresolved defects, fresh bound QC upload with actual verified bytes. A failed run/reason and its events remain immutable; never reuse it for a new decision. Stale run/version and missing proof are 409 errors; refresh the detail before retrying rather than assuming a UI-selected status succeeded.
5. **Defect/rework loop.** The Supervisor opens defects (`POST /handyman/execution-scopes/:executionScopeId/defects`) and FINISHes the old QC run `FAILED` with a reason. The assigned PIC starts rectification with `POST /handyman/defects/:defectId/start-rectification` `{ "expectedVersion": n, "idempotencyKey": "..." }`; after a **new completed PIC Work Session**, uploads `BEFORE_AFTER_WORK` bytes and calls `.../record-rectification` with `{ "expectedVersion": n, "sessionId": "<completed PIC session UUID>", "evidenceReference": "hm-ev://...", "idempotencyKey": "..." }`. Reinspection uses a **new** QC run after the FAIL, not the old run: while new run is OPEN the Supervisor may call `.../pass-reinspection` with `expectedVersion`/key. If reinspection fails again, FINISH the new QC run `FAILED` (reason) **before** `.../request-reinspection` with `expectedVersion`, `reason` and key. That event records server-owned `reinspectionRunId` and retains the previous proof in history while clearing the current proof; repeat with a new session, upload and next run. Finally set every required item and new QC evidence on the new run and FINISH `PASSED`. PIC cannot verify their own rework.
6. **Variation QC and BAST consume, never mint, QC PASS.** Variation `POST /handyman/field/execution-scopes/:executionScopeId/variations/:variationId/qc` must reference the existing `qcRunId` and matching `qcOutcome`; a claimed PASSED must be the latest guarded PASS with full version/item/session/defect/byte verification. Its field evidence remains separately required. BAST `prepareHandymanBast(actorUserId, { executionScopeId, idempotencyKey })` requires the same latest PASS and anchors it as immutable `bast.qcRunId` in a **DRAFT**, unsigned document; it does **not** ISSUE or ACCEPT it. The existing BAST `issueHandymanBast` and customer `acceptHandymanBast` recheck that exact run is still latest/valid. If a new QC run opens, ISSUE/ACCEPT fail; VOID and REJECT remain possible. Customer acceptance still requires a separate governed signature (`POST /handyman/bast/:bastId/accept` or `/sign-off` with `decision: "ACCEPT"`, `signatureDigest` and `idempotencyKey`, `tenant_company.manage` plus Building access). `GET /handyman/execution-scopes/:executionScopeId/bast` and `GET /handyman/bast/:bastId` return `bast.qcRunId` (nullable only for pre-migration history); `acceptance.customerAccepted` and `warrantyStartEligible` remain false at PREPARE/ISSUE. **Do not infer acceptance or financial eligibility from `PASSED` or `DRAFT`.**

**Transport boundary for Operations PR #13:** the existing `handyman-bast-api` HTTP router deliberately exposes customer reads and customer sign-off **only**. Worker/provider `PREPARE`, `ISSUE` and `VOID` are service functions, **not HTTP endpoints**; do not point a frontend button at an invented `/bast/prepare` URL or at `/accept`. If PR #13 needs those buttons, it needs a separate reviewed, Building-scoped worker command transport/permission grant before enabling them. No new BAST engine or automatic customer approval was added here.

## Errors and legacy compatibility

- 403: `BUILDING_ACCESS_DENIED` (sibling/foreign Building), `HANDYMAN_QC_NOT_AUTHORIZED` / `HANDYMAN_DEFECT_NOT_AUTHORIZED` (insufficient assignment or dedicated permission). A frontend persona claim never overrides these.
- 409: `HANDYMAN_QC_CHECKLIST_NOT_CONFIGURED`, `HANDYMAN_QC_CHECKLIST_CONFLICT`, `HANDYMAN_QC_VERSION_CONFLICT`, `HANDYMAN_QC_STALE_RUN`, `HANDYMAN_QC_PASS_BLOCKED`, `HANDYMAN_DEFECT_REINSPECTION_RUN_REQUIRED`, `HANDYMAN_BAST_QC_NOT_READY`. BAST active-conflict and illegal-transition errors retain their prior meaning. A storage-integrity error may be reported by the shared evidence boundary; treat it as blocking PASS.
- Migrations `0442`–`0445` append to the existing QC/defect/variation/BAST history. Old QC runs and BAST records are **not** backfilled with fictional items, version links, events or `qcRunId`. An unguarded historical `PASSED` row is not a new approval: publish/bind explicitly and open a fresh run. Old BAST documents retain `qcRunId: null`; new PREPARE and subsequent ISSUE/ACCEPT are guarded at both service and database boundaries.
