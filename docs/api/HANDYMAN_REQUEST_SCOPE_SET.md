# Handyman Request scope set and operational completion readiness

`GET /api/v1/handyman/requests/{handymanRequestId}/scope-set` is an authenticated read for an active, non-customer Operations actor with `tenant_company.manage`, `handyman.commercial.manage` and an active assignment to the Request's exact Client/Building. It does not mutate a Request or scope.

Each member is an `ORIGINAL` execution scope linked to the same Request, Client, Building, tenant, attribution, quotation, exact APPROVED version and customer decision. All independently approved original scopes remain members, including legacy CLOSED scopes; a later quotation does not cancel or supersede an earlier approval or erase completed work. Warranty rework scopes are not original members. Missing, duplicate, stale, cross-context or unprovable lineage makes the *whole set* `membershipStatus: BLOCKED`; partial members must not be used as a complete set. Historical data is not backfilled or repaired.

Quotation versions are shown separately. An `ISSUED` quotation superseded by another quotation was never an approved scope; superseding an appointment, crew assignment, dispatch, or unapproved quotation is not scope cancellation. There is no established original-scope cancellation/supersession fact in the current lifecycle, so this projection does not invent one or exclude any original scope on that basis. A cancelled pre-commitment Request with a scope is inconsistent and blocked. An empty set is blocked, not evidence of completion.

## Completion and BAST evidence

`completion.status` is `VERIFIED` only when the existing current guarded scope QC PASS and exact verified completion manifest both validate. It exposes the manifest ID/version/hash, verification ID and QC run ID/version. The verified manifest can include PARTIAL or NOT_PERFORMED items: `workState` is `COMPLETED` only when all remaining approved items in that current manifest are completed, otherwise `INCOMPLETE`. For `NOT_VERIFIED` or `STALE_OR_UNVERIFIED`, `workState` is `UNKNOWN`; scope `CLOSED` alone is not proof.

Each scope also has `bastAcceptance`. `VERIFIED` means one active BAST has a unique ISSUE and independently verified customer acceptance/sign-off, and the immutable issued BAST and attested consent match the exact scope, Request, tenant, approved quotation, completion verification, manifest and current QC. The projection verifies historical consent against its recorded actor and context; it does not substitute today's PIC identity. The proof includes the BAST, official document/PDF hash, acceptance event and sign-off identifiers. Missing, unsigned, ambiguous, unverifiable, rejected or stale BASTs cannot satisfy another scope, and an old accepted BAST cannot authorize changed completion or QC. No BAST exemption is established, so a missing BAST blocks readiness. Old BASTs without authoritative immutable completion binding remain unverified rather than being guessed or rewritten.

`completionReadiness` has `status: READY | BLOCKED` and `blockers: [{ code, message, executionScopeId }]`. `READY` requires established membership and, for **every** required ORIGINAL scope, `completion.status: VERIFIED`, `workState: COMPLETED`, and `bastAcceptance.status: VERIFIED`. Membership blockers have `executionScopeId: null`; evidence blockers identify the affected scope. Codes distinguish membership/approval problems from `SCOPE_COMPLETION_UNVERIFIED`, `SCOPE_COMPLETION_STALE`, `SCOPE_WORK_INCOMPLETE`, and BAST issuance, acceptance, integrity, scope-binding or current-completion failures. Multiple blockers can apply at once.

**READY is operational evidence readiness only.** It is not Request CLOSE, financial/invoice or payment reconciliation, delivery, warranty, cancellation, or authorization to close. It does not assert Visit completion or associate sessions with visits. Any eventual close operation must independently check its own current requirements.

## Snapshot pin

`revision` is a Request-local, monotonic approval/scope-set fence, not a new membership or CLOSE record. `fingerprint` pins the current verified and blocked source identities, completion and BAST proof/readiness. Approval, scope, work, QC, BAST issuance or acceptance changes that alter the projection invalidate old pins. Consumers must compare **both** values under the same transaction using `assertHandymanRequestScopeSetCurrent`, keep the resulting locks through their own operation, and independently recheck their own prerequisites. A later close part must also fence or prohibit post-close approvals; this read neither implements nor implies that policy. Downgrade cannot discard the existing revision fences while Requests exist. Legacy execution-scope CLOSE and invoice authorities are unchanged.
