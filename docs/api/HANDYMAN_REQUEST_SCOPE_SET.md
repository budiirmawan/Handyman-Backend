# Handyman Request scope set — PART 01A

`GET /api/v1/handyman/requests/{handymanRequestId}/scope-set` is an authenticated read for an active, non-customer Operations actor with `tenant_company.manage`, `handyman.commercial.manage` and an active assignment to the Request's exact Client/Building. It is not Request CLOSE or a readiness decision.

Each member is an `ORIGINAL` execution scope linked to the same Request, Client, Building, tenant, attribution, quotation, exact APPROVED version and customer decision. All independently approved original scopes remain members, including legacy CLOSED scopes; a later quotation does not cancel or supersede an earlier approval or erase completed work. Warranty rework scopes are not original members. Missing, duplicate, stale, cross-context or unprovable lineage makes the *whole set* `BLOCKED`; partial members must not be used as a complete set. Historical data is not backfilled or repaired.

Quotation versions are shown separately. An `ISSUED` quotation superseded by another quotation was never an approved scope; superseding an appointment, crew assignment, dispatch, or unapproved quotation is not scope cancellation. There is no established original-scope cancellation/supersession fact in the current lifecycle, so this projection does not invent one or exclude any original scope on that basis. A cancelled pre-commitment Request with a scope is inconsistent and blocked. An empty set is blocked, not evidence of completion.

`completion.status` is `VERIFIED` only when the existing current guarded QC and exact verified completion manifest both validate. The verified manifest can include PARTIAL or NOT_PERFORMED items: `workState` is `COMPLETED` only when all remaining approved items in that current manifest are completed, otherwise `INCOMPLETE`. For `NOT_VERIFIED` or `STALE_OR_UNVERIFIED`, `workState` is `UNKNOWN`; scope `CLOSED` alone is not proof. This work state does not assert financial, BAST, delivery, warranty or close requirements.

`revision` is a Request-local, monotonic approval/scope-set fence, not a new membership or CLOSE record. `fingerprint` pins the current verified and blocked source identities and the observed completion state. New quotation decisions, original scopes, quotation version transitions and scope-variation approval changes invalidate old pins. Consumers must compare **both** values under the same transaction using `assertHandymanRequestScopeSetCurrent`, keep the resulting locks through their own operation, and independently recheck their own prerequisites. A later close part must also fence or prohibit post-close approvals; PART 01A neither implements nor implies that policy. Downgrade cannot discard these fences while Requests exist, because doing so could reset published pins. Legacy execution-scope CLOSE and invoice authorities are unchanged.
